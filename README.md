# Banking Data Warehouse & Security Layer

**Status:** Core DWH Complete | Security Layer: RLS Implemented & Tested

A functional Data Warehouse for a simulated banking environment, extended with a Row-Level Security layer using native SQL Server features.

## Project Overview

This project builds a Star Schema Data Warehouse from synthetic banking data (customers, products, dates, branches, and transactions), then layers enterprise-style access controls on top: a dedicated `ETLService` account for loads, and Row-Level Security so analysts only see transactions from their assigned branch.

**What makes this project unique:**

Beyond the standard ETL pipeline and Star Schema modeling, this project implements a working security layer using SQL Server native features:

- **Row-Level Security (RLS):** Restricts analysts to only view transactions from their assigned branches. Status: ✅ Implemented & tested with `EXECUTE AS` across multiple personas.
- **Dedicated service account (`ETLService`):** The ETL pipeline authenticates with SQL Server credentials (not Windows Auth), managed via a `.env` file and `python-dotenv` — never hardcoded in source.
- **Dynamic Data Masking (DDM):** Automatically obfuscates PII (Cedula, Email, Phone) for non-privileged users. Status: ⏳ Planned.
- **Native Server Auditing:** Tracks every SELECT, INSERT, UPDATE, and DELETE on sensitive tables, providing a forensic audit trail. Status: ⏳ Planned.

## Key Features

### 1. Dimensional Modeling (Star Schema)

Star Schema with 4 dimensions (`DIM_Customer`, `DIM_Product`, `DIM_Date`, `DIM_Branch`) and 1 fact table (`FACT_Transaction`).

### 2. ETL Pipeline

Python ETL pipeline (`src/etl_pipeline.py`) that:

- Reads synthetic data generated by `src/generate_data.py` from `data/raw/*.csv`.
- Loads each CSV into its corresponding dimension or fact table.
- Authenticates as `ETLService` using credentials from a local `.env` file (see Setup below).

> **Note:** the tables must be empty before each run (`FACT_Transaction` first, then the 4 dimensions) or the load will fail with a primary key violation, since the generator produces fixed surrogate keys on every run.

### 3. Security Layer

**Row-Level Security (RLS) – Implemented & tested:**
A filtering policy ensures analysts see only their branch's data in `FACT_Transaction`. The predicate function accepts the current user and the row's branch key, cross-references it with `Security.UserBranch`, and returns 1 only if the user is authorized. `AuditCompliance`, `DWHAdmin`, and `ETLService` are exempt from the filter. Tested with `EXECUTE AS` for `LauraGomez`, `CarlosMendez`, `AuditCompliance`, and `DWHAdmin`.

**Dedicated service account:**
`ETLService` is a SQL login with explicit `GRANT`s (SELECT on all tables, INSERT/DELETE/ALTER as needed on dimensions and the fact table) rather than relying on Windows Authentication or `sysadmin` rights.

**Dynamic Data Masking (DDM) – Planned:**
Sensitive columns (Cedula, Email, Phone) will be partially masked for analysts, while auditors and admins see full data.

**Audit Trail – Planned:**
SQL Server's native auditing will capture all access to `FACT_Transaction` and `DIM_Customer`.

### 4. Power BI Dashboards

Interactive dashboards connected to the DWH, displaying:

- Monthly sales trends.
- Top customers by transaction volume.
- Data quality metrics (clean vs. flagged transactions, via `FlagQuality`).

## How to Run This Project

**1. Clone the repository**

```bash
git clone https://github.com/alejandrov07/banking-data-warehouse-etl.git
```

**2. Set up the database schema**

Run the table creation script in SQL Server (as a `sysadmin`/db owner account):

```bash
sql/create_tables.sql
```

**3. Create the security principals and permissions**

Run these scripts in order, inside `sql/security/`, as a `sysadmin` account:

- `setup_principals.sql` – Creates the 5 SQL logins/users (`LauraGomez`, `CarlosMendez`, `AuditCompliance`, `DWHAdmin`, `ETLService`) and the `Security` schema. **Replace the `<P@SSWORD>` placeholders with real passwords before running.**
- `user_branch_mapping.sql` – Creates `Security.UserBranch` and defines which analyst owns which branch.
- `grant_base_permissions.sql` – Grants base SELECT to all principals, plus the INSERT/DELETE/ALTER permissions `ETLService` needs to run the ETL.
- `rls_predicate_function.sql` – Creates the inline RLS predicate function.
- `rls_policy.sql` – Binds the function to `FACT_Transaction` (creates the policy in `OFF` state).
- `rls_index_optimization.sql` – Adds a supporting index on `Security.UserBranch` for predicate performance.

**4. Set up your local environment**

Copy `.env.example` to `.env` in the project root (`.env` is git-ignored and must never be committed):
DB_USER=ETLService
DB_PASSWORD=<the real password you set in step 3>
DB_SERVER=<your SQL Server instance>
DB_NAME=BankingDWH


Install Python dependencies:

```bash
pip install pandas sqlalchemy pyodbc python-dotenv
```

**5. Generate and load data**

```bash
python src/generate_data.py
python src/etl_pipeline.py
```

**6. Activate Row-Level Security**

Once the base data is loaded, turn the policy on:

```sql
ALTER SECURITY POLICY Security.pol_transacciones
ALTER FILTER PREDICATE Security.fn_predicate_transacciones(USER_NAME(), [BranchKey])
ON dbo.FACT_Transaction
WITH (STATE = ON);
```

Verify it with `EXECUTE AS USER = '<name>'` for each of the 5 principals and confirm the row counts match their branch assignments (see the "Row-Level Security" section above for the tested results).

**7. Open the Dashboard**

Open `dashboards/banking_dashboard.pbix` in Power BI Desktop.
